# 课程文档补充：值得明确写入的教学、数据与交付规范

- **版本**：V1.1
- **日期**：2026-08-02
- **定位**：本文件补充课程结构、Notebook 路线图和质量评估中容易被遗漏、但会直接影响学习体验与后续维护的规范。
- **适用对象**：课程设计者、Notebook 编写者、数据集维护者、前端/运行时实现者、测试人员和授课教师。
- **当前课程事实**：109 个连续教学章节 + 8 个独立模块大作业章节 = 117 个课程章节；时间与日期章节目前属于规划内容，尚未进入目录。

> 本文件是“为什么这样设计、还需要提前约定什么”的补充说明，不替代课程内容规范、技术规范和 QA 清单。若发生冲突，以 `COURSE_DOCUMENTATION_INDEX.md` 中列出的当前权威文档为准。

---

## 1. 课程内容不只要“覆盖知识点”，还要覆盖学习行为

每个章节应明确学生在学完后能够完成的可观察行为，而不是只列名词。建议每章至少写出 3 类目标：

1. **理解目标**：能用自己的话说明概念、方法适用场景和限制；
2. **操作目标**：能在独立 Cell 中调用方法、查看结果并处理常见输入；
3. **迁移目标**：能把方法用于一个略有变化的数据或问题，而不是只复现示例。

目标应使用“读取、创建、筛选、转换、比较、解释、可视化、诊断”等动词，避免“掌握、了解、熟悉”这类无法验收的表述。

每章建议增加“完成证据”小节，说明学生提交或自查时应看到什么，例如：

- 能打印输入、处理结果和关键中间变量；
- 能解释一个输出为什么出现；
- 能指出一个边界情况及其处理方式；
- 能独立改动一个参数并比较前后结果；
- 能用本章方法完成一个小型综合任务。

---

## 2. Notebook 应有固定的教学节奏，而不只是单元格堆叠

推荐每个章节遵循以下节奏，并允许根据难度删减，不允许随意打乱：

1. **章节定位**：本章解决什么问题、与前后章有什么关系；
2. **学习目标与前置知识**：告诉学生学什么、需要先会什么；
3. **最小可运行示例**：用最少代码展示概念；
4. **概念拆解**：解释输入、处理、输出和数据类型；
5. **方法/函数逐个说明**：每个重要方法独立 Markdown + 独立代码 Cell；
6. **参数和返回值实验**：至少改变一次参数，观察结果差异；
7. **边界情况与错误示例**：使用短小、可恢复的例子，错误后给出解释；
8. **综合案例**：把本章方法串成完整任务；
9. **结果解释与可视化**：明确“看到了什么、为什么、有什么限制”；
10. **本章小结**：概念、方法、常见错误和迁移提示；
11. **模块大作业入口**：作为模块最后一章之后的独立课程章节，作为模块学习的最终整合。

每个阶段应有清晰 Markdown 标题。不要把“方法表格、十几个示例和综合案例”塞在一个 Cell 中；一个教学动作对应一个 Cell，便于运行、修改、定位错误和后续评估。

## 3. 方法与函数说明需要统一字段

每个核心方法/函数至少写清楚以下内容：

| 字段 | 说明 |
|---|---|
| 名称与调用形式 | 例如 `str.replace(old, new)` 或 `len(obj)` |
| 解决的问题 | 说明为什么需要它，不先讲术语堆砌 |
| 参数 | 参数含义、类型、默认值、是否必填 |
| 返回值 | 返回什么类型；是否返回新对象 |
| 原对象是否改变 | 明确“原地修改”或“返回副本” |
| 最小示例 | 输入尽量短，输出明确 |
| 第二个示例 | 展示不同参数、不同数据或组合用法 |
| 边界情况 | 空值、空序列、大小写、越界、重复值、时区和格式不匹配等 |
| 常见错误 | 类型错误、参数顺序错误、变量未定义、文件/目录副作用或时区误用等 |
| 与相近方法区别 | 例如 `replace` 与 `strip`、`loc` 与 `iloc` |
| 结果解释 | 不仅展示输出，还说明输出说明了什么 |

代码 Cell 应尽量自包含：变量在当前 Cell 内定义，或在上一个紧邻的教学 Cell 中明确创建。若依赖前文变量，应在 Markdown 中标注依赖，不得依赖学生“碰巧按过运行全部”。

不使用 `assert` 作为教学自检。需要检查时，用 `print()` 输出“实际结果、预期观察点和提示”，或用条件分支打印友好信息；错误示例要让学生知道如何恢复，而不是只看到红色 traceback。

---

## 4. 结果输出必须服务于理解

每个重要代码 Cell 都应判断是否需要以下输出：

- **输入输出对照**：展示处理前和处理后；
- **关键变量**：打印形状、类型、长度、缺失数量或汇总统计；
- **标签化输出**：避免只显示一个裸列表或裸数字；
- **小规模预览**：大表只展示前几行、后几行和统计摘要；
- **可视化**：图表必须有标题、坐标轴、图例（有必要时）、单位和数据来源；
- **解释 Markdown**：紧跟输出写出观察结论和限制。

结果解释可采用固定句式：

> 从结果可以看到……；这说明……；但需要注意……；如果修改参数/换一组数据，可能会……。

禁止为了“看起来有输出”而打印大量无解释内容。输出长度、精度和表格列数应受控，保证浏览器版和桌面版都能阅读。

## 5. 公开数据集必须有完整的数据卡片

每个使用外部数据的 Notebook 或模块大作业，至少关联一个数据卡片，包含：

- 数据集名称和任务类型；
- 来源平台：scikit-learn、Kaggle、UCI 或其他公开来源；
- 原始页面或引用标识；
- 下载/快照日期；
- 本地文件路径；
- 文件格式和编码；
- 样本量、字段数和目标字段；
- 字段含义、单位、缺失值规则；
- 许可、署名和再分发限制；
- 是否做过清洗、重命名、采样或脱敏；
- 适合的教学范围和不适合的推断；
- 数据质量风险与潜在偏差。

课堂默认使用本地快照，不要求运行时联网。数据目录、`MANIFEST.json`、Notebook 中的路径和文档中的字段说明必须保持一致。若数据更新，必须增加版本号或快照标识，不能静默覆盖旧文件。

对于 Kaggle 数据，文档应额外记录数据集 slug、下载方式和使用许可；对于 scikit-learn 内置数据，应记录具体加载函数及其版本敏感性；对于 UCI 数据，应记录数据页面名称和原始字段说明。

## 6. 模块大作业还需要写清“允许做到什么程度”

模块大作业不是把所有知识点简单拼在一起。每个大作业应明确：

1. **真实问题**：用一句话描述决策或分析任务；
2. **最小交付物**：数据说明、Notebook、结果解释和结论；
3. **必做范围**：保证初学者可以完成；
4. **选做范围**：鼓励深入但不影响主线；
5. **禁止范围**：例如不要求部署 Web 服务、不要求联网 API、不要求复杂深度学习；
6. **评价维度**：正确性、完整性、解释性、可复现性和表达质量；
7. **阶段检查点**：问题定义、数据检查、方法选择、结果复核、最终报告；
8. **最低通过标准**：运行无致命错误，关键结果有解释，数据来源可追溯；
9. **拓展问题**：改变一个条件后重新运行并比较。

大作业应作为模块最后一章之后的独立课程章节，并与前面章节的综合案例形成递进：前面章节练“一个方法”，模块大作业练“一个完整分析流程”。

建议大作业采用以下统一目录结构：

```text
项目标题
├── 1. 问题定义
├── 2. 数据来源与数据卡片
├── 3. 数据读取与质量检查
├── 4. 探索/预处理/建模
├── 5. 结果输出与可视化
├── 6. 结论、限制和下一步
└── 7. 提交前自查
```

## 7. 初学者需要“错误恢复路径”，而不是只有正确答案

每个章节至少覆盖一类可恢复错误：

- 变量名拼写错误；
- 类型不匹配；
- 索引越界或列名不存在；
- 缺失值或空数据；
- 图表标签缺失；
- 训练集/测试集使用错误；
- 文件路径不正确；
- 包未导入或版本差异。

错误示例应包括三部分：

1. 触发错误的最小代码；
2. 用通俗语言解释 traceback 中最重要的一行；
3. 修复后的独立代码 Cell，并打印修复结果。

不要在同一个 Cell 中连续制造多个错误，也不要把错误吞掉。错误示例的目标是培养诊断习惯，而不是考验学生猜代码。

## 8. 可复现性要从第一章开始，而不是只在机器学习章节出现

所有 Notebook 应遵守：

- 随机过程显式设置随机种子并说明作用；
- 路径使用课程约定的相对路径；
- 不依赖用户本机桌面、下载目录或环境变量；
- 不依赖前一次运行残留的变量；
- 需要的导入集中在章节开头或对应方法前；
- 输出不应依赖当前时间，除非明确用于演示；
- 数据处理顺序稳定，排序规则写清楚；
- 版本敏感 API 标注兼容性提醒；
- 重新启动内核后可以按顺序运行；
- 浏览器版和桌面版都能解释运行差异。

“运行成功”不等于“可复现”。验收时至少要做一次“重启内核 → 运行全部 → 检查关键输出”的冷启动测试。

### 8.1 时间与日期内容的完成检查

如果课程实施日期与时间专题，必须额外检查：

- [ ] 明确 `date`、`time`、`datetime`、`timedelta` 的区别；
- [ ] `today()`、`now()`、`strptime()`、`strftime()`、`combine()`、`timestamp()` 各有独立 Markdown 和 Code Cell；
- [ ] 每个时间函数都有参数、返回值、是否修改原对象和边界说明；
- [ ] 至少覆盖正常日期、跨月/跨年、无效日期、空字符串和格式不匹配；
- [ ] 明确 naive datetime、timezone-aware datetime、UTC 和 `ZoneInfo`；
- [ ] Pandas 中有 `to_datetime()`、`.dt`、时间索引、`resample()`、`rolling()` 的衔接任务；
- [ ] Matplotlib/Seaborn/Plotly 的时间轴示例说明排序、格式化、粒度和时区；
- [ ] 机器学习时间任务使用按时间切分和未来信息泄漏检查；
- [ ] 示例不把当前系统时间当作固定答案，动态输出必须解释其变化原因。

## 9. 数据分析和机器学习章节还应记录方法选择理由

不要只写“调用某个函数得到结果”。应让学生看到方法选择的依据：

- 这是描述性分析、预测还是分类/聚类任务；
- 目标变量是什么，特征变量是什么；
- 为什么采用该切分、缩放、编码或评估指标；
- 哪些方法适合当前数据，哪些方法不适合；
- 基线模型是什么；
- 是否存在数据泄漏；
- 结果能否推广到数据集之外；
- 指标提升是否具有实际意义；
- 可视化是否可能误导读者。

机器学习教学至少区分：训练、验证、测试；拟合、预测、评估；特征处理、模型训练和结果解释。每一步都要打印关键形状或指标，避免“黑箱式一行代码”。

## 10. 需要定义术语、命名和语言风格

建议建立课程术语表，至少统一：

- 对象、变量、参数、返回值、属性、方法、函数；
- 样本、特征、目标、标签、观测；
- 缺失值、异常值、重复值；
- 训练集、验证集、测试集；
- 预测值、真实值、残差、指标；
- 表格、序列、数组、DataFrame、Series。

命名建议：

- 变量名使用有意义的英文或中英结合命名；
- 同一章节不要反复复用会造成歧义的 `data`、`result`；
- 数据集变量名体现来源或用途，如 `iris_df`、`X_train`；
- 输出标签使用中文说明，代码 API 保留英文原名；
- 每章只引入必要的缩写，并首次出现时解释。

---

## 11. 无障碍与多端阅读必须落到 Notebook 内容层

除了页面层面的无障碍，Notebook 内容也应做到：

- Markdown 标题层级连续，不跳级；
- 图表有文字结论，不能只依赖颜色；
- 表格预览不要只靠颜色区分类别；
- 代码输出避免过宽，必要时选择关键列；
- 图表配色兼顾色觉差异，线型/标记同时编码；
- 中英文混排、公式和代码的间距稳定；
- 图片或外部资源不可用时仍有文字说明；
- 手机窄屏下，长代码和宽表格有可理解的阅读方式。

---

## 12. 教师交付和课程维护需要有“变更影响分析”

任何课程内容变更都应记录：

- 变更原因；
- 影响的章节、模块、大作业和数据集；
- 是否需要重新生成 `catalog.json`；
- 是否需要同步 `public/course/` 与 `dist/course/`；
- 是否需要更新数据 Manifest；
- 是否需要重新运行静态审计、冷启动运行和截图验收；
- 是否改变学生已有的学习路径或提交要求；
- 是否需要在变更日志中通知教师和学生。

建议每次修改使用小版本号，并在文档中维护“变更前/变更后/迁移说明”。不要仅修改 Notebook 而不更新课程方案或质量报告。

---

## 13. 学习进度不能只表示“打开过”

进度模型至少区分：

- 未开始；
- 已阅读；
- 已运行示例；
- 已完成章节理解检查；
- 已进入模块大作业；
- 已提交模块大作业；
- 已完成或需要返工。

如果当前产品只支持较简单的进度状态，也应在文档中说明哪些状态是真实测量、哪些只是用户手动标记，避免把“打开页面”误认为“掌握知识”。学习分析数据应尽量采用聚合、最小化和可关闭原则，不收集与教学无关的代码内容。

## 14. 建议建立风险登记表

| 风险 | 影响 | 预防 | 发现后处理 |
|---|---|---|---|
| 数据路径失效 | Notebook 无法运行 | Manifest + 冷启动测试 | 修复路径并更新版本记录 |
| 浏览器/桌面结果差异 | 学生困惑 | 双运行时兼容说明 | 提供差异解释和替代 Cell |
| Cell 依赖隐藏状态 | 按单元运行失败 | 独立示例审计 | 重写为自包含 Cell |
| 输出无解释 | 学生只会复制 | 结果解释覆盖率 | 增加 Markdown 结论 |
| 外部数据许可不清 | 无法发布 | 数据卡片和来源审查 | 更换数据或补充许可 |
| 章节任务与模块大作业重复 | 学习负担过重 | 统一任务分层 | 删除重复正式作业 |
| 版本升级导致 API 变化 | 示例失效 | 锁定版本/兼容标注 | 增加迁移说明 |
| 旧文档误导实施 | 团队执行错误 | 权威索引和历史标记 | 更新索引并标注弃用 |

## 15. 文档完成的定义

课程文档不能只满足“文件存在”。本轮可将以下条件作为完成定义：

- 当前课程事实在所有权威文档中一致；
- 旧版本内容有历史标记，不会被误读为当前规范；
- 每个模块、章节、大作业和数据集都有可追溯关系；
- Notebook 单元格规范、方法说明规范和结果解释规范可执行；
- 数据来源、许可、快照和本地路径完整；
- 运行环境、浏览器版/桌面版差异和网络依赖已说明；
- QA 清单能验证内容、运行、视觉、无障碍、性能和发布；
- 质量评估报告引用了可复现的审计证据；
- 文档变更有日期、版本和影响范围；
- 至少完成一次“文档引用存在性 + Notebook 冷启动 + public/dist 同步”验收。

---

## 16. 推荐的后续文档拆分

当课程继续扩大时，建议将以下内容独立维护，而不是继续堆在一个总方案中：

1. `COURSE_GLOSSARY.md`：术语、命名和中英文写法；
2. `DATASET_CARDS.md`：所有数据集的数据卡片和许可；
3. `CAPSTONE_RUBRICS.md`：8 个模块大作业的统一评分量规；
4. `NOTEBOOK_AUTHORING_GUIDE.md`：教师/内容作者的 Cell 编写规范；
5. `RELEASE_RUNBOOK.md`：从修改内容到发布验收的操作手册；
6. `CHANGELOG.md`：课程结构、数据、Notebook 和运行时的变更记录。

在这些文件尚未拆出前，本补充文件可以作为内容设计和交付验收的统一补充入口。
