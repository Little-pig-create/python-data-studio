## 2. 主要质量问题

### 2.1 方法说明存在重复

同一个方法可能因为调用对象不同而被重复记录，例如：

- `raw.strip`
- `stripped.strip`
- `clean.replace`
- `replaced_all.replace`

这些调用应归并为统一的方法知识点：

- `str.strip()`
- `str.replace()`

同一章内每个方法只保留一套完整说明：

1. 方法定义；
2. 参数解释；
3. 返回值；
4. 是否修改原对象；
5. 独立最小示例；
6. 一个边界示例；
7. 综合案例中的应用。

### 2.2 跨章节重复讲解

可视化章节不应反复完整讲解 `pd.read_csv()`、`fillna()`、`astype()` 等已经在 Pandas 模块学过的方法。

后续章节应区分：

- **本章新方法**：完整讲解并提供独立示例；
- **前置方法**：只说明用途，并链接或提示前置章节。

### 2.3 部分章节过长

机器学习和综合项目章节的单元格数量较多。单章内容过长会降低学习主线的清晰度。

建议控制范围：

| 类型 | 建议单元格数量 |
|---|---:|
| Python 基础章节 | 20～35 |
| NumPy/Pandas 基础章节 | 25～40 |
| 可视化章节 | 25～40 |
| 机器学习专题章节 | 35～55 |
| 模块大作业 | 可更长，但必须分阶段导航 |

### 2.4 缺少保存的代表性运行结果

静态检查只能确认代码具备输出逻辑，不能证明学生看到过正确结果。建议保存少量代表性输出：

- 方法最小示例的文本结果；
- DataFrame 前几行；
- 清洗前后规模；
- 描述统计；
- 代表性图表；
- 模型指标和错误样本。

不要求每个单元格都预执行，但关键教学节点应有示例输出。

### 2.5 结果解释不够统一

每个重要代码或图表示例后，统一增加“结果解读”单元格，回答：

- 输出说明了什么；
- 哪个结果最重要；
- 如果结果异常应该检查什么；
- 该方法的适用范围和限制是什么。

### 2.6 注释仍需从“做什么”提升到“为什么”

不只写：

```python
# 读取数据
```

而应说明：

```python
# 读取固定的本地快照，避免课堂运行依赖外部网络
```

复杂代码单元格至少应包含：当前步骤、选择原因、关键参数和潜在风险。

### 2.7 独立 Cell 需要真正独立

独立示例应满足：

- 必要导入在当前单元格完成；
- 示例数据在当前单元格创建；
- 不依赖隐藏变量；
- 结果直接打印或显示；
- 不修改课程主流程中的共享变量；
- 不产生不必要的临时文件。

### 2.8 方法参数说明不够系统

核心方法应说明参数的含义、默认值、边界和修改效果。例如 `str.replace()`：

```text
str.replace(old, new, count=-1)
```

需要说明：

- `old`：旧文本；
- `new`：新文本；
- `count`：最多替换次数；
- 默认替换全部；
- 返回新字符串；
- 原字符串不变；
- 找不到旧文本时的行为。

### 2.9 可视化章节需要讲清楚图表选择

每个可视化章节都应回答：

- 这个图适合解决什么问题；
- 横轴、纵轴、颜色和分组分别表示什么；
- 哪些参数改变统计含义；
- 哪些参数只改变外观；
- 数据量过大时会有什么问题；
- 图表是否可能产生误导；
- 何时选择静态图，何时选择交互图。

### 2.10 机器学习章节需要强化防泄漏意识

机器学习章节统一检查：

- 预测目标和预测时点；
- 训练集、验证集、测试集；
- 不可用字段和数据泄漏；
- 简单基线模型；
- 预处理是否只在训练集拟合；
- 类别不平衡；
- 指标选择；
- 错误样本和业务成本；
- 模型结论的适用边界。

### 2.11 数据来源说明需要补齐

只要 Notebook 使用数据文件，就应注明：

- 数据集名称；
- 原始来源；
- 本地路径；
- 数据规模；
- 主要字段；
- 目标字段；
- 本地快照日期；
- 是否抽样或清洗；
- 数据使用限制。

## 9. 方法讲解单元格的标准模板

每个新方法只允许保留一个主讲解区，推荐使用以下结构：

```markdown
### str.replace()

**作用**：把字符串中的旧文本替换成新文本。

**调用形式**：`text.replace(old, new, count=-1)`

**参数**：
- `old`：要查找的文本；
- `new`：替换后的文本；
- `count`：最多替换次数，默认替换全部。

**返回值**：返回一个新字符串，原字符串不变。

**边界情况**：找不到 `old` 时不会报错，结果通常与原字符串内容相同。
```

紧接着放一个独立代码单元格：

```python
text = "python,python"

once = text.replace("python", "Python", 1)
all_items = text.replace("python", "Python")

print("原文本:", text)
print("只替换一次:", once)
print("全部替换:", all_items)
```

再增加一个简短结果解释单元格：

```markdown
### 结果解读

`count=1` 只替换第一次匹配；默认值会替换全部匹配。两个结果不同，说明参数会改变方法行为。原变量 `text` 没有被修改。
```

## 10. 独立示例验收规则

一个示例只有同时满足以下条件，才可以标记为“独立示例”：

- 代码单元格可以从干净内核直接运行；
- 必要的导入、常量和示例数据在本单元格中可见；
- 不依赖前面单元格创建的隐藏变量；
- 运行后产生明确输出；
- 输出带有标签、单位或列名；
- 不覆盖章节主流程中的变量；
- 不要求访问外部网络；
- 不生成未经说明的临时文件。

如果示例必须依赖前置状态，应明确标记为“综合流程单元格”，不能标记为“独立方法示例”。

### 13.2 每章预计学习时长与难度标签

建议在课程目录和每章开头增加学习负荷信息，避免学生只根据章节数量估计任务量。

#### 推荐字段

| 字段 | 示例 | 说明 |
|---|---|---|
| 建议时长 | 25 分钟 | 包括阅读、运行、修改参数和课堂自检 |
| 难度 | 入门 / 基础 / 进阶 / 综合 | 使用统一四级标签 |
| 必做内容 | 示例 1～3、课堂自检 | 明确最低完成范围 |
| 选做内容 | 扩展图表、挑战问题 | 供学有余力者使用 |
| 常见卡点 | 索引越界、数据类型、执行顺序 | 让学生提前知道风险 |
| 推荐练习方式 | 边运行边修改 | 指导学习行为 |

#### 建议的时长口径

- **10～20 分钟**：单一基础语法或方法；
- **20～35 分钟**：多个方法的组合练习；
- **35～50 分钟**：数据清洗、图表分析或模型流程；
- **50 分钟以上**：综合案例或模块大作业阶段。

应在文档中说明：建议时长是面向具备前置知识学生的估计，不包含环境故障排查和首次安装时间。

### 13.3 术语表与统一命名规范

课程跨越 Python、NumPy、Pandas、可视化和机器学习，术语混用会增加初学者负担。建议建立课程级术语表。

#### 应统一的术语

| 不建议混用 | 建议标准写法 | 说明 |
|---|---|---|
| 方法 / 函数 / API | 按对象关系区分 | `str.replace()` 是方法；`len()` 是函数；API 是更广泛的接口概念 |
| 行 / 记录 / 样本 | 在不同上下文明确使用 | 表格中优先“行/记录”，机器学习中优先“样本” |
| 字段 / 列 / 特征 | 明确边界 | DataFrame 中使用“列”；建模输入中使用“特征” |
| 标签 / 目标 / 因变量 | 明确教学阶段 | 机器学习中统一为“目标变量（标签）” |
| 缺失值 / 空值 / NaN | 说明技术含义 | `NaN` 是常见数值缺失表示，不等于所有空字符串 |
| 训练 / 拟合 | 明确关系 | 模型通过 `fit()` 在训练数据上拟合参数 |

#### 价值

- 降低术语迁移成本；
- 提高文档、Notebook、页面和作业描述的一致性；
- 便于后续翻译、搜索和自动检查。

---

### 13.4 代码风格、命名和教学代码规范

建议把代码规范从“风格建议”升级为可审核的课程标准。

#### 推荐规则

1. 变量名表达业务含义，不使用无意义的 `a`、`b`、`tmp`；
2. 使用 `snake_case` 命名变量和函数；
3. 常量使用大写或在 Markdown 中明确说明；
4. 不在同一示例中复用不同含义的变量名；
5. 每个代码单元格只完成一个明确步骤；
6. 对关键参数使用命名参数，提升可读性；
7. 输出必须带标签、单位或字段名；
8. 禁止使用宽泛异常捕获掩盖错误；
9. 随机过程必须设置随机种子并解释其用途；
10. 文件操作章节优先使用 `os` 和内置 `open()`；其他章节使用课程统一路径写法；
11. 不将密码、令牌、邮箱、个人数据写入教学 Notebook；
12. 不使用不稳定的网络实时抓取作为课堂必需步骤。

#### 建议增加“代码审阅清单”

```text
[ ] 变量名是否能说明数据含义？
[ ] 代码是否有不必要的隐藏依赖？
[ ] 输出是否能让学生核对结果？
[ ] 注释是否解释了原因而非重复代码？
[ ] 是否存在会覆盖原始数据的危险操作？
[ ] 是否记录了随机种子、数据版本和关键参数？
```

---

### 13.5 错误处理、排错与求助规范

学生使用 Notebook 时，最常见的问题不是算法，而是执行顺序、变量状态、路径和环境。建议把排错流程写为统一协议。

#### 推荐排错顺序

1. 阅读完整错误信息，尤其是最后一行异常类型；
2. 确认当前单元格是否依赖前面未运行的变量；
3. 打印类型、长度、形状、列名和缺失值数量；
4. 核对文件路径、文件名和工作目录；
5. 将输入缩小到最小复现样例；
6. 重启内核，从上到下运行；
7. 仍无法解决时，按规范提交求助信息。

#### 标准求助模板

```text
章节：第 XX 章
单元格标题：
运行环境：浏览器 Notebook / 本地 Jupyter
完整错误信息：
已尝试步骤：
输入数据规模与关键字段：
预期结果：
实际结果：
```

#### 价值

- 让学生学习调试而不是只等待答案；
- 让教师或助教快速复现问题；
- 形成可分析的课程问题库。

---

### 13.6 数据治理、许可与隐私规范

公开数据集不代表可以不做说明。建议为每个数据文件增加统一的数据卡（Data Card）。

#### 数据卡最小字段

| 字段 | 说明 |
|---|---|
| 数据集名称 | 课程中使用的名称 |
| 原始来源 | Kaggle、UCI、scikit-learn、官方开放数据等 |
| 原始链接或来源标识 | 保证可追溯，不要求 Notebook 运行时联网 |
| 许可证或使用条件 | 明确教育使用和再分发限制 |
| 下载/快照日期 | 固定课程使用版本 |
| 本地路径 | 课程运行路径与源数据保存路径 |
| 数据规模 | 行数、列数、文件大小 |
| 抽样和清洗 | 是否取子集、随机种子和筛选规则 |
| 包含的敏感字段 | 是否存在个人信息、地理位置、联系方式等 |
| 教学限制 | 不能用于的结论或不应推广的范围 |

#### 隐私与安全原则

- 不将学生真实作业、姓名、邮箱或成绩作为公开示例数据；
- 不将访问令牌、密码、Cookie、数据库连接字符串写入 Notebook；
- 对可能包含个人信息的数据进行脱敏、聚合或替换；
- 对金融、医疗、招聘、教育等高风险案例明确“仅用于教学，不用于真实决策”。

---

### 13.7 无障碍与可读性规范

Notebook 的教学质量不仅取决于代码正确，也取决于不同学习者是否能读懂和操作。

#### 建议标准

- 图表不能只依靠颜色传达类别，应同时使用标签、形状、线型或直接标注；
- 图表提供清晰标题、坐标轴、单位、图例和数据来源；
- 避免红绿作为唯一的正负或通过/失败区分；
- Markdown 标题层级连续，不跳级；
- 长表格提供简短结论，不把关键信息只放在大表中；
- 中文、英文、代码和数字之间保持合理空格与标点；
- 图表配色在深色和浅色背景下均应可辨识；
- 关键图表应补充文字版结论，方便无法直接阅读图形的学习者；
- 代码块保持适中行宽，避免一行塞入复杂链式调用。

---

### 13.8 模块大作业的里程碑、评分与反馈机制

模块大作业不应只在最后给出完整任务，应拆成可检查的里程碑。

#### 推荐里程碑

| 阶段 | 学生交付物 | 教师/系统检查 |
|---|---|---|
| 问题定义 | 一段问题说明、目标变量和成功标准 | 是否可回答、是否可量化 |
| 数据审计 | 数据字典、缺失值和异常值报告 | 是否理解字段和数据限制 |
| 基线方案 | 最小可运行分析或基线模型 | 是否能从头运行 |
| 核心分析 | 图表、指标或模型结果 | 是否与问题匹配 |
| 结果解释 | 结论、证据和限制 | 是否避免过度推断 |
| 最终交付 | Notebook、摘要、图表和复现说明 | 是否完整、规范、可复现 |

#### 评分设计建议

除最终分数外，建议记录：

- 过程完成度；
- 代码可复现性；
- 数据解释能力；
- 图表表达质量；
- 模型或分析的局限说明；
- 反思与改进能力。

这会避免学生只追求“跑出一个结果”而忽略过程质量。

### 13.9 教学版本管理与变更日志

Notebook 内容、数据快照和依赖版本变化都会影响可复现性。建议建立课程版本策略。

#### 应记录的变更

- 章节内容新增、删除、重排；
- 方法示例修订；
- 数据文件替换或抽样规则变化；
- 依赖库版本变化；
- 模型参数、随机种子和指标变化；
- 大作业评分规则变化；
- 已知问题和修复状态。

#### 推荐规则

- 课程大版本：结构或学习路径发生变化；
- 小版本：示例、文案、图表或数据修订；
- 修订版本：错别字、路径、代码兼容性修复；
- 每个 Notebook 元数据中可选记录课程版本与最后审阅日期；
- 数据快照版本必须与 `MANIFEST.json` 对应。

### 13.10 运行环境、依赖与离线策略

当前课程需要同时考虑浏览器 Notebook、前端静态资源和本地运行环境。文档应明确最低运行要求。

#### 建议写清楚

- 支持的浏览器与推荐版本；
- Notebook 内核类型和 Python 版本；
- 必需核心库及推荐版本范围；
- 课程静态数据文件如何映射到 `/datasets/`；
- 无网络情况下哪些内容仍可运行；
- 外部网络资源不可用时的替代方案；
- 字体、中文显示和图表渲染的已知限制；
- 内存不足、图表过慢和大文件读取的降级策略。

#### 降级策略示例

```text
数据文件过大
→ 使用课程提供的固定子集
→ 明确抽样规则和随机种子
→ 提示完整数据适用于课后扩展
```

### 13.11 学习分析与反馈数据（仅在合规前提下）

如果未来记录学习进度，应先在文档中定义数据最小化原则。

#### 可以记录的低风险教学指标

- 章节开始与完成状态；
- 运行失败的错误类别，不保存完整敏感输入；
- 课堂自检完成状态；
- 模块大作业里程碑状态；
- 学生主动标记的“需要复习”章节；
- 章节平均完成时长的匿名聚合结果。

#### 不建议默认记录的内容

- 完整代码内容；
- 学生本地文件路径；
- 访问令牌、Cookie 或环境变量；
- 未脱敏的个人数据；
- 与教学无关的设备信息。

所有学习分析功能都应说明用途、保存期限、访问权限和退出机制。

### 13.12 教师交付与内容维护流程

建议把“新增或修改一章 Notebook”的流程写成标准操作，避免长期维护后风格漂移。

#### 推荐流程

1. 定义学习目标和前置知识；
2. 选择本章唯一的核心问题；
3. 确定本章新增方法，不重复讲解已学方法；
4. 编写独立最小示例；
5. 编写组合案例；
6. 添加结果解读、常见错误和课堂自检；
7. 补充数据卡和路径说明；
8. 从干净内核运行；
9. 进行同伴审阅；
10. 更新变更日志、质量评估和课程目录。

#### 建议增加的审阅角色

- **内容作者**：负责正确性和教学目标；
- **技术审阅者**：负责可运行性、路径、依赖和性能；
- **教学审阅者**：负责由浅入深、案例难度和结果解释；
- **数据审阅者**：负责数据来源、许可和隐私；
- **发布负责人**：负责目录、版本和浏览器端同步。

### 13.13 成功指标与发布门槛

如果没有量化标准，后续改造很容易停留在“感觉更好”。建议在文档中定义最低发布门槛。

#### 建议发布门槛

| 维度 | 最低要求 |
|---|---|
| 文件完整性 | 109 个连续教学章节 Notebook 和 8 个独立模块大作业 Notebook 可解析 |
| 关键代码 | 每个模块至少抽样 2 章从干净内核运行通过 |
| 独立示例 | 抽查的独立示例无隐藏变量依赖 |
| 数据合规 | 所有使用数据文件的章节具备数据来源和本地路径说明 |
| 结果解释 | 每章至少 1 个重要示例有结果解读 |
| 图表质量 | 图表具有标题、坐标轴/图例和文字结论 |
| ML 质量 | 所有 ML 综合章节包含基线、切分和泄漏检查 |
| 模块作业 | 8 个模块大作业从头运行并有交付物说明 |
| 可访问性 | 核心图表不只依赖颜色；关键结论有文本表述 |
| 文档同步 | 方案、路线图、评估报告和数据清单版本一致 |

---

## 14. 建议的文档维护节奏

| 节奏 | 需要更新的内容 |
|---|---|
| 每次修改一个 Notebook | 变更记录、该章数据卡、运行结果和审阅记录 |
| 每完成一个模块 | 模块知识依赖、抽样运行记录、作业评分反馈 |
| 每次课程发布前 | 质量评估、依赖版本、数据清单、已知问题和发布门槛 |
| 每学期或课程批次结束 | 学习反馈、常见错误库、案例难度和时长估计 |

文档不应只在首次设计时编写。它应成为课程内容、数据、运行环境和教学反馈之间的持续连接层。
